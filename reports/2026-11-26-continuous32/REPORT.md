# 五人连续出块与百节点测试准备

一次选出五位出块者，按名单顺序各连续生成 32 个实际区块，正常一轮共 160 块。漏块不计入 32 块。成员出满 32 块后，下一位从下一时间片开始出块。

父块时间片为 `p`、当前成员尚未出满 32 块时，`p+1..p+8` 仍由该成员出块；这八个时间片均没有新区块，从 `p+9` 开始由下一位接管。随后每经过八个完整空时间片再跳过一位。默认时间片为 200 毫秒，八个空时间片共 1.6 秒。

出块顺序编号和本次已出块数写入区块，参与摘要和签名。节点从父块恢复顺序，验证同步、重启及分叉后的新区块。名单外节点恢复出块前，先让名单中的五位各获得八个时间片。

新建链默认配置：

```json
{
  "producer_rotation": true,
  "epoch_blocks": 160,
  "consecutive_blocks": 32,
  "producer_timeout_slots": 8,
  "slot_ms": 200
}
```

参数绑定创世配置，创建新链后启用。已有链省略 `consecutive_blocks` 时继续原有规则。GUI 新建链使用以上默认值，并显示“连续出块”和“出块超时”。

## 性能修改

- 正常出块时，跨成员交接次数降为原来的 1/32。保留五人十条直连、下一轮提前连接和接替成员优先发送。
- 主循环先提交已经收到的区块，再构造本地区块，减少基于旧父块生成区块。
- 缓存同一分支、同一选举周期的 VDF 上下文，最多 32 项。分支的源区块哈希参与缓存键，分叉重放读取对应分支的数据。
- 连续出块记录每块增加 16 字节；完整扩展上限相应增加到 2424 字节，紧凑区块消息使用相同上限。

## 百节点操作

沿用上次 100 台主机的地址，生成每节点八个普通邻居、共 400 条连接和四个交易入口的计划。实际地址、账户数据和操作脚本保存在本机独立目录，Git 中不包含登录凭据。

1. 开机前使用 `cluster_quick.py prepare` 生成计划并校验签名交易。数据文件和账户创世文件可跨 Windows/Linux 复用；Linux 控制机核对摘要后直接发送。
2. 先开启一台构建机，完成源码构建和全部回归。`cluster_release.py --runtime-dir` 检查程序、共享库及 EL9 兼容性，生成一个分发包。
3. 再开启其他测试主机，以 32 路并行分发相同程序和运行库。每台主机运行一个节点，无需逐台编译。
4. 正式测试默认 300 秒，预热两秒；统计 30 秒后，连续三个至少 15 秒的区间 TPS 均低于目标 70%，且每个区间的交易积压均增长，则提前停止。
5. 保存 TPS、确认时间 P50/P95/P99、重组次数、资源和账户状态，停止测试进程并清理本轮数据库。复测使用 `--staged`，校验已安装文件后直接开始，不重复分发。

测试默认关闭节点内部时钟纠偏，使用已同步的主机时钟；其他线程、区块上限和步长沿用上次设置。完整参数与命令见 [集群文档](../../ansible/CLUSTER.md)。

## 验证

Release 完整构建通过，42 项 CTest 全部通过，耗时 581.05 秒。七进程测试覆盖完整的五人各 32 块、连续成员停块接管、错误计数和提前接管拒绝、分叉后的出块顺序、同步和重启后的账户一致性。前端 32 项测试通过；Ansible 工具 139 项，127 项通过、12 项因平台条件跳过；原有指标测试 12 项通过。

首次完整回归发现紧凑消息测试使用旧扩展上限，以及本机 MinGW 线程退出时 GMP 临时对象析构崩溃。已更新消息边界测试，并在 MinGW 的每次 VDF 调用中管理临时对象，避免在线程退出时访问已经释放的 TLS 内存。修复后原语连续十次测试通过，共创建 320 个并发工作线程；2,023,424 次迭代生成的证明与官方向量相同，随后完整回归通过。

本地提前校验 3,050,000 笔交易、1024 个账户，正文 536,800,000 字节；10,000 TPS 测量使用前 3,020,000 笔。首次完整校验耗时 553.739 秒，复用数据清单仅核对文件摘要，耗时 0.453 秒。数据只需上传到控制机，其他节点通过交易协议接收。

详细结果和修复记录见 [VALIDATION.json](VALIDATION.json)。百节点 TPS 测试等待服务器开启后执行。
